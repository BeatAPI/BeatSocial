# BeatSocial 架构

写给设计者和维护者：系统由哪些部分组成、数据怎么流、有哪些不能破的约束。

## 1. 角色和边界

| 角色 | 在哪里 | 负责 | 不负责 |
|---|---|---|---|
| 审核台（本项目） | Mac 本地 | 唯一正本：账号、帖子、版本、媒体槽、审批、回执、指标、竞对、规则；校验和统计 | 不发帖、不写稿、不抓数据 |
| Claude Code / Codex | Mac 本地，每周新会话 | 批量写稿、拆解竞对、独立审稿 | 只按主人明确决定代为批准；不发布 |
| Grok bots | 云端盒子，通过 Shell 调用 Mac 上的 `beatsocial` | 发布、读回核验、回执、24h/7d 采数据、周复盘数据、竞对抓取 | 不改已批准的稿、不采纳规则 |
| 主人 | 看板 + Claude Code 对话 | 在对话里批稿、批规则、确认配额 | 不在网页上操作 |
| Git（数据目录） | 私有仓库 | memory/ 和数据库文本备份的版本历史 | 不存媒体和实时数据库 |

**业务入口**：BeatSocial MCP 和兼容的 `beatsocial` 命令，共用 `core.Store`。网页是只读看板（服务器默认拒绝一切写请求）；主人的决定在 Claude Code 对话里说，由 Claude 代为执行，批准、采纳规则、确认配额都要带上主人原话（`--owner-said`），记进操作记录。没有人直接改数据库。

## 2. 目录

```text
beat-social/                 程序（可开源，不含任何运营数据）
  beatsocial/model.py        标准词表：状态、平台、市场、指标字段
  beatsocial/db.py           SQLite 表结构
  beatsocial/lint.py         批准前检查（阻断 / 需核价 / 提醒）
  beatsocial/core.py         全部业务操作（Store 类）
  beatsocial/cli.py          beatsocial 命令行
  beatsocial/server.py       本地网页和 JSON 接口（只监听 127.0.0.1）
  beatsocial/mcp_server.py   MCP stdio 协议、生命周期与错误响应
  beatsocial/mcp_tools.py    对话工具定义、参数校验、版本冲突和审批检查
  beatsocial/legacy.py       旧审核台 plan.json 一次性迁移
  web/                       审核台页面
  prompts/                   写稿、审稿、复盘、竞对、bot 的标准提示词
  tests/                     端到端测试

beat-social-data/            你的数据（私有 Git 仓库）
  beatsocial.db              SQLite 正本（不进 Git）
  backup/db.sql              数据库文本导出（进 Git）
  memory/                    LESSONS、打法卡、复盘、配额、竞对拆解（进 Git）
  media/                     图片和视频（不进 Git）
  work/<周>/                 写稿包、稿件 JSON、审稿包（临时工作区，不进 Git）
```

## 3. 数据模型

| 表 | 一行是 | 关键字段 |
|---|---|---|
| accounts | 一个渠道账号 | id（如 X-JP）、platform、country、lang、handle、bot、per_week、slot_times、types、rules、status |
| posts | 一个帖子位 | id（W47-X-JP-03）、account_id、week、slot_at（北京时间）、type、benchmark_id、status、current_v、approved_hash、claimed_by、published_url |
| versions | 帖子的一个版本 | text、reply_thread、zh_ref、writer_note、author |
| media | 一个媒体槽 | slot、kind（image/video）、spec（要求）、file |
| metrics | 一个时段的指标 | period（h24/d7/d30）、impressions…followers_delta、extra（平台特有字段） |
| competitors / samples | 竞对 / 对标样本 | 平台、市场、类型、开头、结构、指标、怎么替换 |
| rules | 一条写法规则 | scope（global / platform:x / country:JP / account:X-EN / type:比价）、status（proposed/active/rejected/retired） |
| events | 一条操作记录 | 谁、什么时候、做了什么，所有写操作都留痕 |

「市场 × 渠道」由帖子所属账号决定：每个账号只属于一个平台、一个市场、一种语言。

## 4. 帖子生命周期

```text
todo 待写 ──写稿 import──▶ review 待审 ──批准（绑定内容哈希）──▶ approved 已批准
   ▲                          │  ▲                                  │
   │                     打回 ▼  │ 改稿                    bot claim → 发布 → receipt
   │                    rejected 打回                               ▼
   │                                                        published 已发布 ──d7 指标──▶ measured 已回测
   └──────── 任何改稿 / 换素材：批准失效，回到 review ◀───────────────┘（发布前）
```

不变量：
1. **批准绑定版本**：approved_hash = 正文 + 首评 + 媒体文件（路径、大小、修改时间、inode）的哈希。内容变了哈希就变，`queue` 不再交给 bot。对话批准还绑定主人看到的版本：MCP 必须携带 revision，CLI 使用 --hash。只有主人明确决定后，AI 才能携带原话代为批准；交互终端仍可确认。原话留痕不是身份认证。
2. **阻断不可绕过**：占位符、竞品价、缺素材、空正文时，批准（含批量批准）直接拒绝；含价格的稿必须在批准时确认核价。标记每次读取时现算，不存库，没人能手动清掉。
3. **不重复发**：发之前必须带着 queue 给的 hash 去 claim（原子操作，2 小时锁，同时只有一个 bot 能领到；hash 不符说明批准后内容变了，领不到）；没到发布时间不能领；这条以前被领过（含别的 bot 过期的领取）时会返回提醒，先查平台再发；回执只能由领取它的 bot 写；第一个链接生效，之后不同的链接会被拒绝，人工更正要加 `--force`。
4. **未知不是 0**：指标拿不到就是 NULL；一个值都没有时拒绝写入；同一时段分几次写入时，后写的只补充字段，不会把先写的清空。
5. **只认 media/ 里的文件**：媒体槽只能指向数据目录 media/ 下的文件，网页也只提供这个目录里的文件。
6. **时间统一北京时间**：带时区的时间（Z、+09:00）写入时自动换算。
7. **网页默认只读**：默认拒绝写请求。原兼容开关开启写入后仍校验 Origin、Host 和 JSON 格式；本轮保持该旧兼容行为。
8. **规则先提案后生效**：AI 只能 propose；只有主人采纳的规则进入 LESSONS.md 和写稿包。

## 5. 五条流程

### 批量写作
`plan <周>` 按账号的每周条数、发布时间和 memory/quota 配额生成帖子位，并给每个位配对标 → `brief <周>` 为每个账号生成写稿包（打法卡路径、生效规则、近两周最好/最差、每个帖子位的对标和上次打回意见）和稿件 JSON 模板 → Claude 填稿 → `draft import` 校验入库，返回检查结果 → `review pack` 交给独立 AI 审稿 → `review import` 记录结论（版本不符的结论自动作废）。

### 竞对参照
samples 表存对标样本。生成帖子位时自动挑选：同平台 → 同市场 → 同内容类型 → 被用得少 → 曝光高，同一周同一账号不重复用同一条。写稿包把对标的开头、结构、数据和「怎么替换成我们的」列给写稿 AI。每周由 Grok 按 prompts/竞对刷新.md 补新样本。

### 数据回收与迭代
bot 用 `metric due` 看该采什么，`metric add/import` 写入。周一 `retro <周>` 生成复盘数据（各账号、各市场、最好最差 3 条、漏发、缺数据）和下周配额建议（同账号内按内容类型中位曝光：前 1/3 加 1、后 1/3 减 1，总量不超过每周条数 ±30%）。复盘 AI 补结论并提交规则提案；主人 采纳规则、确认配额；下次 `plan` 和 `brief` 自动用上。

### 数据统计
`stats --by account|country|platform|type|week|bot`，同一套口径：已发、有数据、中位曝光、总曝光、最高、中位赞、互动率、缺数据。曝光优先取 d7，没有用 h24。

### 渠道账号管理
accounts 表 + 网页「账号」页。新增账号时自动建打法卡 memory/playbooks/<ID>.md。账号的 bot 字段决定谁能在 queue 里看到它的稿。

## 6. 并发、离线和备份

- SQLite WAL 模式，所有写操作用 `BEGIN IMMEDIATE` 事务，多个 bot 同时调用命令不会写坏数据。
- Mac 离线：初版不支持离线发布。`queue` 只把到点的稿放进 items，未到点的放进 upcoming；离线发布需要后续加独占授权、撤稿同步和素材同步。
- 配额：复盘写入 memory/quota/<周>.json（suggested）；只有人确认（confirmed）后才生效，并一直沿用到下一份确认的配额。样本少于 3 条的内容类型不参与调整。
- 复盘文件：数据部分在标记之间，重跑只刷新数据部分，复盘 AI 写的结论保留；复盘/本周复盘.md 只指向最新一期。
- 备份：`beatsocial backup`导出 backup/db.sql、重新生成 LESSONS.md，并提交到数据目录的 Git。建议让 Grok 每晚 23:00 跑一次；推到私有 GitHub 仓库需要你先在数据目录 `git remote add`。
- 媒体：迁移时用硬链接，不占额外空间；新素材直接放进 media/，在稿件里写相对路径。

## 7. 开源边界

程序目录不含任何账号、密码、Token、客户数据或运营内容。别人使用时：`beatsocial init <自己的数据目录>`，通过 MCP 或 CLI 建自己的账号即可。市场、平台词表在 model.py，增加时同步改本文和网页。

## 8. 已知限制（初版）

- 时间统一按北京时间存储和显示；受众时区只用于展示，还没有按当地时间排期。
- 点击和注册归因没有接入（需要先决定落地页参数）。
- 网页没有登录，只能本机访问；协作者要访问需另做部署。
- 配额算法很简单，样本少时意义有限；复盘 AI 应该结合样本量判断。

## 9. 增量 MCP 接入

详见 [MCP 接入与对话流程](MCP接入与对话流程.md)。MCP 是新增接口；原 UI、HTTP 行为、CLI 操作和数据结构没有在这次接入中重写。上文描述的旧网页批准路径不是新对话流程。当前网页默认只读，旧服务仍有显式开启写入的兼容开关。

MCP 使用独立 revision 覆盖正文、首评、中文参考、媒体字节摘要、排期及账号身份；保留原 content_hash，避免使既有记录整体失效。所有新接口的帖子写入先对比 revision，批准绑定主人已看过的 revision，批量批准全成或全败。MCP 默认要求独立审稿通过，允许主人明确、留痕地人工覆盖。MCP 对已领取帖子拒绝修改，不提供发布、领取或回执工具。

这些附加校验位于 MCP 适配层，不能宣称旧 CLI 或 HTTP 写入口也获得了同样校验。所有业务写入继续调用 Store。主人的原话和执行者分别留痕，但同机 shell 操作者仍能调用 CLI，因此不是身份隔离。

## 9. 内容逻辑与配图（2026-11-11）

- 中文（大陆）市场移出 BeatSocial：MARKET_ORDER 只含英文、日文、韩文、繁中、俄语；CN 账号暂停，旧数据保留。
- 数据目录的 `memory/内容策略.md` 是写稿的总纲（代码仓库只带模板 `prompts/内容策略.template.md`）：先讲「Agent + API 把事办成」，价格做佐证；固定栏目同一渠道一天最多 1 条、一周最多 3 条；同一天同语言两个渠道不撞同一句话。写稿包里列出同一天其他渠道已写的主题。
- 各渠道打法卡在数据目录 memory/playbooks/，按主人的《写法》和《定位与渠道》写成，复盘后更新。
- `beatsocial make-media <帖子>`：把帖子正文和媒体槽要求交给 Codex CLI，按 beatapi-social-visual 技能（浅色银灰 3D / 暖色纸雕，标识左下角）出 1 张 PNG，存到 media/<周>/ 并挂到媒体槽；没出图就报错，不会挂空文件。Codex 路径可用环境变量 BEATSOCIAL_CODEX 指定。
- 校验里的「竞品价」只针对竞对平台（fal、Higgsfield、OpenRouter 等），BeatAPI 上在卖的模型（Kling、Veo 等）写自家价格不算。

## 10. 多图与存储（2026-11-11）

- 一条帖子可以有多个媒体槽（第 1、2、3 张……），默认一张；看板按顺序显示，queue 按 slot 顺序交给 bot，批准哈希包含每一张。校验按平台限制张数：X 4 张且不能视频和图片混放，Threads / LinkedIn 20 张，Telegram 10 张。
- SQLite 是运行时正本；数据目录的 Git 只保存 memory/ 和 backup/db.sql（每晚导出），用于版本历史和异地备份。媒体文件不进 Git，需要另外的备份（Time Machine 或外置盘）。
- 代码仓库（可开源）和数据仓库（私有）分开，开源时不会带出任何账号、稿件或数据。
